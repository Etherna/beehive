# Beehive

Beehive is a utility to manage a cluster of [Bee Swarm](https://github.com/ethersphere/bee) nodes. It is an **ASP.NET Core application** (not a set of libraries): it exposes a REST API to register and interact programmatically with different Bee nodes, acts as a Bee-compatible Swarm gateway in front of the cluster, and runs an async task engine (Hangfire) for recurring operations like automatic scheduled cashout. It uses a MongoDB instance to keep cluster configuration and cached/persisted Swarm data.

## Build, run, test

Target framework is **.NET 10** with `TreatWarningsAsErrors=true` and `AnalysisMode=AllEnabledByDefault` (and `Nullable=enable`, `EnableNETAnalyzers=true`) on every project — warnings break the build.

```bash
dotnet restore Beehive.sln
dotnet build Beehive.sln -c Release
dotnet test  Beehive.sln -c Release                 # runs the three xUnit test projects
dotnet test test/Beehive.Persistence.Tests/Beehive.Persistence.Tests.csproj           # single project
dotnet test --filter "FullyQualifiedName~BeehiveDbContextDeserializationTest"          # single class
dotnet test --filter "FullyQualifiedName~BeehiveDbContextDeserializationTest.BeeNodeDeserialization"        # single test
dotnet run  --project src/Beehive                   # local dev server, listens on http://localhost:1633
```

There is no frontend build step: the host has only a minimal Razor Pages landing page plus static `wwwroot` assets (no npm, no bundler). A plain `dotnet build` produces a runnable host.

Running the app requires a reachable **MongoDB** instance — supply `ConnectionStrings:BeehiveDb` and `ConnectionStrings:HangfireDb` (config or environment), plus `Elastic:Urls` for the Serilog sink and the `ASPNETCORE_ENVIRONMENT` variable. The easiest way to run locally with its dependencies is the Docker Compose sample under [samples/docker-beehive-sample](samples/docker-beehive-sample). `Directory.Build.props` sets `NuGetAuditMode=direct`, so only direct package vulnerabilities are audited.

Docker: `docker build .` (uses `Dockerfile`, which runs `dotnet test` as part of the build stage and exposes port `1633`).

## Architecture

Four-project layered solution, plus three mirror test projects (`Beehive.Tests`, `Beehive.Services.Tests`, `Beehive.Persistence.Tests`). Root namespace is `Etherna.Beehive[.<Layer>]` and the namespace mirrors the folder path under it.

- **`src/Beehive.Domain`** (`Etherna.Beehive.Domain`) — Pure domain layer. Entities live flat under `Models/` (e.g. `BeeNode`, `Chunk`, `ChunkPin`, `PostageBatchCache`, `PostageStamp`). Base classes: `ModelBase`, `EntityModelBase`, `EntityModelBase<TKey>`. Domain events under `Events/` are dispatched via `Etherna.DomainEvents`. It holds no persistence contract: the db context interface, and the interface of any repository, are declared in `Beehive.Persistence`. Depends on `Etherna.Scrinium.Core`, `Etherna.DomainEvents`, `Nethereum.Web3`, and `SwarmSdk` (Swarm value types like `SwarmHash`, `SwarmReference`, `PostageBatchId`).
- **`src/Beehive.Persistence`** (`Etherna.Beehive.Persistence`) — Scrinium implementation and its contract. `IBeehiveDbContext` is the db context interface the other layers use (repositories + a GridFS `ChunksBucket` + the `IEventDispatcher`), and `BeehiveDbContext` implements it, declaring the repositories and their indexes; `ModelMaps/` defines how each entity serializes; `Repositories/DomainRepository` is a generic repository that dispatches domain events on create/delete, `Repositories/SwarmChunksRepository` the repository of `swarmChunks`, with its interface `ISwarmChunksRepository` beside it; `Serializers/` holds custom BSON `SerializerBase<T>` implementations for SwarmSdk value types (`SwarmHash`, `SwarmAddress`, `SwarmReference`, `SwarmUri`, `PostageBatchId`). References `Beehive.Domain` only.
- **`src/Beehive.Services`** (`Etherna.Beehive.Services`) — Application services and side effects. `Domain/` holds services that orchestrate domain operations (`BeeNodeService`, `DataService`, `PinService`, `PostageBatchService`). `EventHandlers/` follows the `On<Event>Then<Action>Handler` convention and is auto-discovered by reflection in `ServiceCollectionExtensions.AddDomainServices` — any `IEventHandler` (typically via `EventHandlerBase<TEvent>`) placed in this namespace is registered automatically. `Tasks/` holds Hangfire jobs split by trigger (`Cron/`, `Trigger/`, `Background/`). `Utilities/` holds `BeeNodeLiveManager` (the singleton tracking live node status) and `BeehiveChunkStore`. `Options/` holds configuration objects. References `Beehive.Domain` and `Beehive.Persistence`: the services reach the db through `IBeehiveDbContext`.
- **`src/Beehive`** (`Etherna.Beehive`) — ASP.NET Core host (Minimal APIs + a minimal Razor Pages site). `Program.cs` wires everything: the Minimal API endpoints, three OpenAPI documents + Scalar API Reference, Scrinium (a scoped db context over a singleton engine) with Hangfire (Mongo storage), Serilog → Elasticsearch, CORS, the Scrinium admin dashboard at `/admin/db`, the Hangfire dashboard at `/admin/hangfire`, and in Development only the debug pages of `Configs/DebugPages` (`/debug/config` prints the whole configuration, `/debug/request` the request as received). The API lives under `Areas/Api/`; cross-cutting host code is under `Configs/`, `Extensions/`, `JsonConverters/`, `Options/`. References all three other projects.
- **`test/Beehive.Persistence.Tests`** (xUnit + Moq) — focuses on model-map deserialization: each `ModelMap` GUID/schema version is pinned by a stored BSON document and asserted to deserialize into the expected entity.

### API design

The API is built with **Minimal APIs**, not MVC controllers — this is the central pattern to follow when adding endpoints:

- Routes are registered in static `*ApiMapper` classes (`BeehiveApiMapper`, `SwarmApiMapper`) and mounted from `Program.ConfigureApplication` via `app.MapBeehiveApi()` / `app.MapSwarmApi()`. Each mapper builds a `RouteGroupBuilder` and tags it with a **marker** (`BeehiveApiMarker`, `SwarmApiMarker`, `SwarmV1ApiMarker`).
- Every route delegates to a **handler interface** (`IBeehiveApiHandler`, `IBytesApiHandler`, `IChunksApiHandler`, …) implemented by a `sealed` handler class in `Areas/Api/` or `Areas/Api/SwarmApiHandlers/`, registered `AddScoped` in `Program`. Handler methods return `Task<IResult>` and wrap their body in `ExceptionHandler.RunAsync(ApiVersion.X, async () => { … })`.
- Responses are serialized with the curated `JsonSerializerOptions` in `Configs/CommonConsts` (camelCase + the SwarmSdk/Beehive JSON converters): return `Results.Json(dto, CommonConsts.BeehiveV04JsonSerializerOptions)` (or `SwarmJsonSerializerOptions`). DTOs use the `Dto` suffix (`Areas/Api/DtoModels/`), request bodies use the `Input` suffix (`Areas/Api/InputModels/`).
- **Every error passes through `ErrorResults.GetErrorResult`, and each API branch has its own error body.** The Swarm branch answers bee's status shape, `{"code":404,"message":"Not found"}` (`BeeErrorDto`), the one bee clients read. The Beehive branch answers the message as a JSON string (`Results.Json(message, statusCode)`, so a 404 carries `"Not found"` as `application/json`): the shape decided for the Etherna services' own APIs, first shipped on etherna-sso; the routes of `BeehiveApiMapper` declare it with `Produces<string>(statusCode)` on every error status, so the OpenAPI document describes it. Never serialize an MVC action result (`ObjectResult`) as data: `Results.Json` doesn't execute it, its properties become the body.
- **A bee route answers bee's status body where bee writes one**: `POST /pins/{reference}` answers a new succeeded pin with 201 `{"message":"Created","code":201}` and a reference already pinned with 200 `{"message":"OK","code":200}` (`BeeStatusDto`, declared with `Produces<BeeStatusDto>` on both statuses), as bee's `jsonhttp.Created` and `jsonhttp.OK`; the SwarmSdk generated client deserializes that body, and fails on an empty one. Beehive's own `/ev1` routes answer what they choose.
- There are **three OpenAPI documents**, each registered with its own `AddOpenApi` pipeline in `Program` and filtered to its marker via `MetadataFilterDocumentTransformer<TMarker>`: `beehive04` (Beehive's own management API), `swarm` (a Bee-node-compatible Swarm API, no prefix), and `swarmv1` (the same surface under `/v1`). The Swarm surface mirrors the Bee HTTP API so SwarmSdk's generated client can talk to Beehive as if it were a Bee node. Transformers live in `Configs/OpenApi/`.

### Key cross-cutting points

- **OpenAPI binary request bodies must be inlined.** Binary upload bodies (`[FromBody] Stream`) must be emitted inline as `{type: string, format: binary}`, never as `$ref: #/components/schemas/Stream` — NSwag (the SwarmSdk client generator) mishandles a `$ref`-to-binary *request* body and produces a JSON-serialized DTO that breaks uploads (responses keep `$ref: Stream`, which NSwag maps correctly to a streaming response, so the component stays). **Two mechanisms are both required and non-redundant**: `BinaryRequestBodyDocumentTransformer` (registered in all three `AddOpenApi` pipelines) fixes the `.Accepts<Stream>` endpoints by matching the resolved `Type==String && Format=="binary"` schema, and the `AcceptsUnrestrictedOperationTransformer` fix handles `/bzz` (`.AcceptsUnrestricted<Stream>`), which the document transformer cannot catch. Don't "simplify" by deleting either one.
- **Arrays of Swarm models get their items from `SwarmModelsSchemaTransformer`.** The json schema exporter describes a type serialized by a custom converter (`SwarmHash`, `SwarmReference` and the other Swarm models) with an empty schema: a property keeps it as the component of its type, which the transformer fills in, but an array drops it and comes with no `items`, so that NSwag would type it as a collection of `object`. The transformer builds the element schema of every array that has none (`GetOrCreateSchemaAsync`), which references the component of the element type; the SwarmSdk `beehive-openapi.yaml` regenerated from the documents relies on it.
- **Scrinium change tracking is snapshot based, with no annotations.** Loaded entities are proxies generated at compile time by the Scrinium source generator (shipped with the `Etherna.Scrinium.Core` package referenced by the Domain project): keep every property and mutating method of a model `virtual`, so the proxy can intercept it for lazy loading and change candidate marking. On save, only the members whose serialization differs from the loaded document are written.
- **The db context is scoped.** Every consumer must be scoped or transient: a singleton capturing `IBeehiveDbContext` pins it (and its identity map) for the process lifetime, and scope validation is on in every environment, so it throws at resolve. A singleton that needs the db (`BeeNodeLiveManager`) opens a scope per access through `IServiceScopeFactory`; startup code touching the db resolves it from a scope (`Program.SeedDbContext`). Entity models are always referenced, never embedded: a member of an entity type must be serialized with a reference serializer in every schema, or the engine build fails.
- **Reference delete policies replace hand-rolled cleanups.** `ChunkPinMap.ReferenceSerializer` takes an explicit `OriginDeleteMode`, declaring what happens to the documents hosting the reference when the pin is deleted through its repository, propagated in background by Scrinium's `DeleteDocDependenciesTask` on the `DB_MAINTENANCE` queue: `Chunk.Pins` declares `RemoveReference`, so `PinService.TryDeletePinAsync` only deletes the pin and the chunks lose its reference afterwards. Declare the policy explicitly for every new reference to a deletable entity: the library default (`RemoveReference`) writes `null` into a non-nullable single member.
- **Beehive has no access control, by design, as bee has none.** The dashboards (`/admin/db`, `/admin/hangfire`), the admin pages (`/admin/chunks-migration`, `/admin/pins-imports`), the management API (`/deprecated-chunks`, `/nodes`, `/stamps`, ...) and the Swarm surface answer whoever reaches them: the dashboards' `AllowAllFilter`s are intentional, and no endpoint checks a principal, an address or a header. The boundary is the network: beehive is a private backend, deployed with no published port on internal overlays, reached by the gateway (the authenticated and metered front of the Swarm surface) and by the operators over the admin VPN. Don't add an address based admission policy to the host (the one tried in 0.4.12 was rejected): inside the overlays it repeats the decision the network already takes, with one more configuration to keep aligned, and behind a proxy it can't tell the client at all. Beehive reachable from a public path is a defect of the infrastructure in front of it, fixed there, never in beehive.
- **Implicit lazy loads throw.** The db context runs with `ImplicitLazyLoad = ReactionMode.Throw` (`Program.cs`): a reference member loads as a summary (`Chunk.Pins` items carry the id only), and reading a member the summary doesn't carry throws `ScriniumLazyLoadingException` instead of querying silently. Before reading anything else, preload explicitly with `dbContext.LoadValuesAsync(models, m => m.Member, ...)`. Queries expressed over references (`c.Pins.Any(p => p.Id == id)`) are rendered server side and read nothing.
- **Model map IDs are fresh random GUIDs.** Every `MapRegistry.AddModelMap<T>("<guid>")` call (and every map inside a `ReferenceSerializer` config) needs a brand-new, randomly generated GUID (e.g. `uuidgen`) that collides with no existing map ID anywhere in the solution — never copy, edit, or hand-craft one. The ID permanently identifies that schema version; a collision silently corrupts serialization. When you add or change a map, add a matching deserialization test in `Beehive.Persistence.Tests` that pins the GUID against a sample document.
- **Index definitions are strongly typed.** In `BeehiveDbContext` `IndexBuilders`, always select fields with lambda expressions (`Builders<BeeNode>.IndexKeys.Ascending(n => n.ConnectionString)`), never magic strings — this keeps compile-time safety against renames.
- **Domain events fire from persistence.** `BeehiveDbContext.SaveChangesAsync` dispatches the accumulated `EntityModelBase.Events` after saving, and `DomainRepository` additionally dispatches `EntityCreatedEvent`/`EntityDeletedEvent` (plus custom events) on create/delete. To get this behavior a repository must be wired as `DomainRepository<T, TKey>` rather than the plain `Repository<T, TKey>` — choose deliberately (in `BeehiveDbContext`, `BeeNodes`, the lock repositories and `ChunkPins` are `DomainRepository`; `ChunkPushQueue`, `Chunks`, `ChunksMigrations`, `PostageBatchesCache`, `PostageStamps` are plain `Repository`, and `SwarmChunks` is a `SwarmChunksRepository`, which extends the plain one).
- **Hangfire queues and jobs.** Queues are declared in `Services/Tasks/Queues.cs` (`DB_MAINTENANCE`, `DOMAIN_MAINTENANCE`, `NODE_MAINTENANCE`, `PIN_CONTENTS`) and pinned in `Program.AddHangfireServer` alongside `"default"`. The Hangfire **server is not started in Staging** (see the `!env.IsStaging()` guard). Recurring jobs are registered in `Program.ConfigureApplication` via `RecurringJob.AddOrUpdate<I…Task>(…, task => task.RunAsync(), Cron.…)` using each task's `TaskId` const. Each job runs in its own DI scope (a fresh db context) with the async-local execution context of Scrinium opened by its Hangfire filter, plus the one of the Etherna.DomainEvents library opened by `Configs/Hangfire/DomainEventsExecutionContextFilter` (its event dispatcher throws `ExecutionContextNotFoundException` without it, and a job inherits none from a request), so a task opens nothing by hand. Code running outside both requests and jobs opens the two contexts itself: `PushChunksBackgroundService` per work cycle (`DbExecutionContextHandler`), `Program.SeedDbContext` for the startup seeding. A job method taking a `CancellationToken` parameter (`IImportNodePinsTask.RunAsync`, `IPinChunksTask.RunAsync`) receives Hangfire's token of the job, the enqueue call passing `CancellationToken.None`. Hangfire cancels it at a graceful shutdown, and within 5 seconds (its `CancellationCheckInterval`) when the job is no longer in `Processing` for that worker: deleted, or taken by another worker. The cancelled job must leave its work resumable and let the `OperationCanceledException` out: Hangfire re-queues it after a shutdown, and ends that performance without a state change when the job was taken (`ImportNodePinsTask` leaves the import running, `PinService.PinChunksAsync` releases the pin lock and leaves the pin not processed). Hangfire.Mongo keeps a fetched job with its worker by a heartbeat, a write each minute issued one after the other, and hands the job to another worker when its `SlidingInvisibilityTimeout` of 5 minutes passes without one, whatever the state of the worker performing it: the jobs of a crashed replica are picked up after that time. A heartbeat write left without an answer on a dead connection stops the heartbeat silently, the driver waiting forever by default: `Program.cs` appends `socketTimeoutMS=30000` to the Hangfire connection string, unless it declares its own, so that write fails, is retried on another connection, and the job stays with its worker (the timeout holds for every operation of Hangfire on its own db, all short; the jobs' work goes through the other connections). On a handover the new performance starts first and the old one is cancelled afterwards: a job that must not overlap itself waits on a lease, as the pins import does.
- **Tasks are split by trigger.** `Tasks/Cron/` = recurring jobs (e.g. `CashoutAllNodesChequesTask`, `CleanupOldFailedTasksTask`, `NodesAddressMaintainerTask`); `Tasks/Trigger/` = enqueued-on-demand jobs (e.g. `PinChunksTask`); `Tasks/Background/` = `IHostedService` workers (e.g. `PushChunksBackgroundService`, gated by config `PushChunks:Enabled`). Each task exposes an `I<Task>` interface and is registered `AddTransient`.
- **`BeeNodeLiveManager` is a singleton** that tracks the live status of registered Bee nodes; it is started in `Program` via `app.StartBeeNodeLiveManager()`, which only starts the heartbeat. **The heartbeat round is the only code calling the nodes for their status**: every 10 seconds, and at once when a node is registered, updated or removed (`RequestHeartbeat`), it syncs the registered nodes with the db, falls back to the dev node when none is registered, refreshes every node in parallel and reads the chain state from one healthy node. A node is registered without being called (`TryAddBeeNode`, used by the round's db sync, the `OnBeeNodeCreated…`/`OnBeeNodeDeleted…` event handlers of the seeding and the api, and the first access to a node registered by another replica), so a node that doesn't answer never holds the startup nor a request: until its first round its status reads not alive, with the default heartbeat timestamp. It reads the nodes through a DI scope opened per access, never through a captured db context. The timer runs the round (`HeartbeatCallbackAsync`) as an async void callback, where an escaping exception terminates the process: the round catches every exception, logs it at Error (`BeeNodesHeartbeatFailed`) and leaves the next tick to run a new round. Any code added to the round stays inside that catch.
- **Every call to a node is bounded by the SwarmSdk client, by the class of its operation** (`SwarmClientTimeouts`, the SDK defaults: 5 seconds for a read the node answers from its own state, like health, readiness, addresses and a batch it owns; 30 seconds for a chain read, like the chain state; up to 10 minutes for a transaction wait or a content transfer), and beehive sets no bound of its own (`BeeNodeLiveInstance` builds the client with the defaults). A node that doesn't complete a call within its bound throws `SwarmClientTimeoutException`, a `TimeoutException` whose message names the call and the bound (`SwarmClient.GetHealthAsync did not complete within 5 s`): the heartbeat marks the node not alive with that message as the reason, and `ExceptionExtensions.IsBeeNodeCallFailure` counts a `TimeoutException` as a node failure, so the stamps endpoints and the upload verification report it as the node's reason too. **A node failure a request path doesn't catch is answered 503 or 504, never 500**: `ExceptionHandler` answers a `TimeoutException` (the client's bound elapsed: `SwarmClientTimeoutException`) with 504 and its message, the way bee answers its own gateway timeouts and the SwarmSdk retries them as transient, and every other exception `IsBeeNodeCallFailure` reports (`SwarmSdkApiException`, `HttpRequestException`, `SocketException`, `TaskCanceledException`) with 503 and the node's reason (`GetBeeNodeFailureReason`), both logged at Warning, a node's 404 staying a 404: a download whose chunk a node doesn't serve in time, a batch purchase or a global batches read the node doesn't complete are problems of the node, not of beehive.
- **A bee node that cannot answer degrades the stamps endpoints, it doesn't fail them.** `GET /stamps` and `GET /stamps/{batchId}` report a batch whose owner node is not alive, or answered an error, from `PostageBatchesCache` (`PostageBatchResult` built from the cache: depth, immutability, utilization from the buckets, `usable` false) with an `error` carrying the node's reason: the heartbeat errors for a node marked not alive (`BeeNodeStatus.NotAliveReason`, the node is not called), the `message` of the node's error body or the exception message otherwise (`ExceptionExtensions.GetBeeNodeFailureReason`, the same reason `ExceptionHandler` writes in a 503 body). A 404 from the node is its answer, not a failure: the batch is not found, as one beehive doesn't know. The values the cache doesn't know (`amount`, `batchTTL`, `blockNumber`, `exists`) are omitted from the JSON, never written as `null`: the SwarmSdk generated client reads them as non-nullable value types, and a JSON `null` fails its deserialization. A batch the cache doesn't know is not found on `GET /stamps/{batchId}`, by design: the cache is the truth, and a lookup on the nodes for every miss would let any caller fan one request out to every node (the fix tried in 0.4.12 was rejected for this); an upload on such a batch is refused the same way. A batch bought outside beehive enters the cache through an import of the node's batches with their buckets, the postage batches work of the next release, after which beehive is the only one stamping with it.
- **The resource locks are Scrinium's resource leases.** `IPinService.AcquireLockAsync`, `IPostageBatchService.AcquireLockAsync` and `TryAcquireChunkPushLockAsync` take their locks through `IBeehiveDbContext.TryAcquireResourceLockAsync`, one namespace per kind of resource (`ResourceLockNamespaces`: `chunkPins`, `chunkPushes`, `chunksMigrations`, `nodePinsImports`, `pinChecks`, `postageBatches`), exclusive or shared by the caller's flag: a lock is the lease document `namespace/resourceId` of the db context lock collection (`_db_lock`), acquired atomically on the server, renewed in background by the `IResourceLockLease` answered for as long as it lives (the default lease of 10 minutes is how long a dead holder keeps the resource), released by its dispose, and lost on `LeaseLostToken`. A long operation under a lease observes that token: `PinService.PinChunksAsync` runs on a token linked to it, so a lost lease stops the reads and the writes, never declares the pin, and is thrown as `ResourceLockException` (the pins import defers such a pin like a locked one); `ImportNodePinsTask` runs on a token linked to the lease of its import, and stops without writing the import when it is lost; `DataService.UploadAsync`, whose chunking takes no cancellation token, checks it once the chunks are stored and records nothing on the batch (stamps, push queue, pin) when the lease is lost. The short holders (`TryDeletePinAsync`, the dilution and the top-up of a batch) don't, nor does the push cycle: its chunk refs are claimed one by one by an atomic update, so a second pusher of the batch pushes other chunks. A denied acquisition throws `ResourceLockException` from the services, while `TryAcquireChunkPushLockAsync` answers null and the push loop skips the batch. Beehive has no lock model, collection, index or cleanup task of its own: the `chunkPinLocks`, `chunkPushLocks` and `postageBatchLocks` collections of 0.4.11 and the `cleanupExpiredLocksTask` recurring job of Hangfire are removed by hand at the 0.4.12 deploy, as its release notes say.
- **An upload is refused before anything is stored when its batch isn't usable on its owner node.** `DataService.UploadAsync` calls `PostageBatchService.VerifyPostageBatchUsableAsync` inside the batch lock, right after the cache lookup: a batch with no `PostageBatchesCache` entry throws `PostageBatchNotFoundException` at the lookup itself (a batch beehive doesn't know is not found, wherever that is detected); an owner node not alive throws `BeeNodeUnavailableException` with the heartbeat reason (`BeeNodeStatus.NotAliveReason`), without a call; the node's 404 throws `PostageBatchNotFoundException`; a batch not usable throws `PostageBatchNotUsableException`; any other failure of the call is a `BeeNodeUnavailableException` carrying the node's reason (`ExceptionExtensions.GetBeeNodeFailureReason`: the `message` of the error body, or the exception message). `ExceptionHandler` answers them as bee's own upload endpoints do: 404 `batch with id not found`, 422 `batch not usable yet or does not exist`, 503 with the reason (`ErrorResults` holds the messages). `PATCH /stamps/topup` and `PATCH /stamps/dilute` refuse a batch the same way before calling the node: 404 `batch with id not found` for a batch beehive doesn't know, 503 for an owner node not registered anymore (`PostageBatchService.GetPostageBatchOwnerNode`, shared with the upload verification). `PushChunksBackgroundService`, on a 404 of the owner node, abandons the queued chunk refs of the batch, setting their `FailedAttempts` to the maximum, the final state of any failed push. The `PostageBatchesCache` entry of a batch its node reports as gone is left as it is.
- **The push queue never loses a chunk for a node that is away.** `PushChunksBackgroundService.TryProcessWorkAsync` searches the next postage batch to push with a read, and claims a chunk ref (`HandledDateTime`) only under the push lock of its batch: the refs of a batch another instance is pushing stay untouched. A failure of the chunk alone (beehive can't read it, or the node refuses it with a 4xx other than 404) charges its `FailedAttempts` and the cycle goes on with the batch; the chunk is tried again a minute later, and at 100 attempts it is abandoned: logged at Error (`ChunkPushAbandoned`), never claimed again, left in queue. A node that can't take the chunks charges nothing: an owner node not registered, not alive for the heartbeat (no call is made), not answering or answering 5xx defers the whole batch for a minute, in the memory of the instance (`deferredBatches`), and its refs wait as they are, however long the node is away. Nothing drops the pushes of a node: the cycle never deletes a ref it didn't push, and the refs of a node removed from beehive wait like the ones of a node away.
- **A chunk the db refuses fails the operation writing it.** `BeehiveChunkStore.AddAsync` puts the chunk in its saving buffer and writes the buffer to `swarmChunks` when full (`FlushSaveAsync`, also called by the owner at the end of an upload and by the dispose); a refused write propagates its exception to the writer (the SwarmSdk hasher pipeline inside `DataService.UploadAsync`, the chunk and soc uploads), so the request answers 500 at the first failure and nothing is recorded as succeeded, no postage stamps, no push queue, no pin. The store never answers `false` for a failure: in the sdk contract of `IChunkStore.AddAsync` a `false` means "already present", and the pipeline feeds the next stage whatever the store answered. The chunks of a refused write stay in the buffer, readable, and a store whose write failed doesn't write again: every further add or flush throws the same failure at once, without a db round trip, and its dispose (and finalizer) leaves the buffer alone, so the writer's exception stands instead of a second failure. The fail-fast matters because the SwarmSdk hasher pipeline (`ChunkFeederPipelineStage`) feeds every chunk of the stream before observing a failed stage task: with a retry per add, a refused upload of more chunks than the buffer would cost one failed db round trip per remaining chunk and answer only at the end.
- **A single owner chunk nobody wrote is not found.** `GET /soc/{owner}/{id}` reads the chunk at the soc address of the identifier and the owner through `BeehiveChunkStore.TryGetAsync`, which answers null when neither the db nor the nodes hold it: `SocApiHandler.ResolveSocAsync` throws `KeyNotFoundException` (404 in bee's error shape), never a failure of beehive; data found at that address that isn't a single owner chunk is a `SwarmChunkTypeException` (400).
- **The contents pinned on a bee node are imported into beehive's own pins by `ImportNodePinsTask`**, one Hangfire job per node on the `PIN_CONTENTS` queue, started by `POST /nodes/{id}/pins/imports` with the `unpin` query flag, one node at a time, and from the admin page `/admin/pins-imports`. `NodePinsImport` (`nodePinsImports` collection) is the record of one run on one node with its counters (`GET /nodes/{id}/pins/imports` for one node, `GET /nodes/pins/imports` for every node, newest first); A run takes every pin of the node, or only the `RequestedReferences` given at start (the `references` of the request body, or the textarea of the admin page). `NodePinImport` (`nodePinImports`) is the record of one pin within a run, referencing its run through `Import` (`OriginDeleteMode.DeleteReferencingDocument`: a deleted run takes its records with it): its outcome (imported, already pinned, failed), the chunks missing or invalid on the node, the failure reason, whether the import unpinned the node (`UnpinnedByImport`, the action; whether the content is on the node now is read from the node, `isOnNode` null when it can't be asked) (`GET /nodes/{id}/pins/imports/{importId}/pins`; the finished runs of a node are deleted by `DELETE /nodes/{id}/pins/imports?failed=`, completed, failed or both, their records following by the delete policy; a running one is never deleted). `NodePinsImportService` starts one import at a time per node (423 while one runs), fails an import whose Hangfire job is gone (`IHangfireJobsMonitor`) whenever it reads one, so both listings, the admin page and a new start report it failed, and snapshots the contents pinned on a node right now with the ones beehive doesn't hold in full (`GET /nodes/{id}/pins/not-imported`). A pin locked by another operation is deferred, not failed: the run retries the deferred pins once at its end, and records a pin still locked then as failed with the lock reason. A run whose job is cancelled, by a shutdown or because another worker took the job, leaves the import running, and the next run of the job starts it again from the first pin. One run at a time works on an import, under the exclusive lease `nodePinsImports/<importId>` it holds until it ends: a run that finds it held waits for it, asking again every `ImportLeaseRetryPeriod`, because a job handed to another worker starts there before its previous performance is cancelled, and two runs on one import contend its pins (the new one would fail the pin the old one is on). A run whose lease is lost stops without writing the import. The chunks are read from the node being imported, never from the nearest healthy node: a content pinned on a node lives in that node's local store only; a chunk beehive already holds is not read again. `PinService.PinChunksAsync` is the pinning itself, shared with `PinChunksTask` (which reads from the healthy nodes), answering the pin and the invalid chunks met: it builds its own `BeehiveChunkStore` over the source node, with the pin attached to every chunk the store saves (`onSavingChunk`), so a chunk read from a node enters `swarmChunks` pinned, and a chunk beehive held already takes the pin by an add-to-set on its document; a chunk counts as pinned only when a document took the pin, and before the pin is declared the service reads back the hashes of the chunks carrying it (in `swarmChunks` and in the deprecated `chunks`), moving to the missing ones every chunk the traversal met whose document doesn't: `TotPinnedChunks` is the number of documents carrying the pin, never the traversal count. A reference beehive declares pinned is checked first (`IPinIntegrityService.CheckPinAsync`, below) and skipped only when its check finds it whole; one found incomplete is reset and pinned again from the node in the same run (the repair of the pins declared succeeded by 0.4.11 while holding nothing). A pinning that succeeded is checked again before its outcome: the node is unpinned only when that check finds the content whole, and a content the check contradicts is recorded failed (`chunks missing in beehive after the import`) and reset, so a new import completes it. A single owner chunk reference is pinned as its single chunk, as bee does: the SwarmSdk `ChunkTraverser` reports the SOC root as found and doesn't enter its wrapped chunk, so the pin succeeds with one chunk, the SOC document carrying the pin. Running the import again with `unpin` unpins on the node the contents imported earlier. The dev node (`DevNodeClient`) keeps in memory the chunks uploaded to it and the pins of the chunks it holds, and starts clean, with nothing uploaded nor pinned.
- **The integrity of a pin is read from beehive's own chunks only.** `PinIntegrityService.CheckPinAsync` traverses the content of a pin with a `BeehiveChunkStore` built with `readFromNodes: false`, which answers not found for a chunk the db doesn't hold instead of asking the nodes: a chunk a node would serve is not a chunk beehive holds. It counts the chunks of the content (`total`, the ones the traversal met, found or not), the missing ones (not in `swarmChunks`: a chunk the store finds in a deprecated store has no document there, and is missing) and the invalid ones (a content addressed chunk whose payload doesn't hash to its address, verified with `SwarmCac.IsValid`; a single owner chunk document that doesn't verify fails its build in the store, and is counted invalid when it is the root, as bee pins a soc as its single chunk; a chunk that is the chunk at its address but not a well formed node of the tree, a `SwarmChunkFormatException` of the traversal, which stops there: `PinCheckResult.MalformedChunk` names it, and the chunks of the content not met before it are not counted). A chunk held without the pin among its references takes it on the spot, by the same add-to-set of the pinning on its `swarmChunks` document, and counts as held: the check repairs a reference, never a chunk. The check reads `swarmChunks` only, so it is asked only once the deprecated stores are empty: `VerifyPinsCanBeCheckedAsync` throws `DeprecatedChunksNotMigratedException` (answered 409 with its message by `ExceptionHandler`) while the deprecated `chunks` collection or the deprecated GridFS bucket hold a document or a file, read through `IDeprecatedChunkStores`. `GET /pins/check` verifies it before anything else, and so does `NodePinsImportService.StartImportAsync`, since an import checks the pins it works on: until the chunks are migrated neither a check nor an import starts. What a migration leaves in the deprecated stores as failed keeps them refused, until the operator removes it. `ResetPinAsync`, under the pin's exclusive lock, brings a pin its check contradicts back to not succeeded with the missing and the invalid chunks as its `MissingChunks`, and deletes the documents of the invalid chunks from `swarmChunks` (`DeleteManyAsync` by hash): the pinning reads beehive's chunks first, and would take the corrupt copy again. The malformed chunk is never deleted: its payload is the chunk at its address, a node would serve the same one.
- **`GET /pins/check` follows bee's handler (`pkg/api/pin.go`), not its counting.** Same route (swarm and `/v1`), same `ref` query, same stream: `application/x-ndjson`, chunked, one `{"reference","missing","invalid","total"}` object per line (properties in reading order, the total after its parts), for the given reference or for every pinned reference, by the age of its first pin, written as each reference is checked; a reference has one line however many pins hold it (an upload with a pin of a content pinned already leaves a second `ChunkPin` of the same reference): every pin of it is checked, each one taking its place among the references of the chunks, and the line is the check of the last one; a reference beehive doesn't pin answers its line with every count at zero, as bee does, never 404; a content with a malformed chunk answers its line too, with that chunk among the invalid ones, so the check of every pin goes on to the next pin instead of ending its stream there; a check of every pin while another one runs answers 429 `pin integrity check of all pins already running`, held across the replicas by the lease `pinChecks/all`; while a deprecated store holds chunks every check, of a reference or of every pin, answers 409 `the deprecated chunk stores are not empty: migrate their chunks first` (`IPinIntegrityService.VerifyPinsCanBeCheckedAsync`), before taking the lease. The counting differs on purpose: bee iterates the chunk addresses it recorded in the pin collection at pinning time, so its `total` is the size of that collection and a pin that recorded nothing reads whole with total 0; beehive traverses the content, so a pin declared succeeded with chunks it never held reads incomplete. The endpoint corrects no pin and deletes nothing.
- **A write conflict the db context couldn't retry away answers 409, not 500.** Scrinium saves and creates run in a transaction on the replica set and retry its transient failures; a transaction that still loses a write conflict surfaces as a `MongoException` labeled `TransientTransactionError`. `ExceptionHandler` answers it 409 Conflict with `ErrorResults.WriteConflictErrorMessage` ("Concurrent write conflict, retry the request", the wording of the other Etherna services) on both API branches, logged at Warning: the request is legitimate and the client repeats it, a 500 would read as a failure of beehive. The same driver exception without the label stays a 500.
- **Bad data stored by a client answers 422 with what is wrong, not 500.** `GET /feeds/{owner}/{topic}` on an update whose payload is arbitrary bytes (a client following the v1 shape without a reference): the SDK reads its first bytes as the span of a chunk that doesn't exist and refuses the decode as `SwarmChunkFormatException`, the exception it throws for any chunk that is not well formed (a span no chunk trie can hold or declaring a redundancy level that doesn't exist, data not as long as the span implies, an encrypted chunk not filling the chunk) and for a tree whose children don't hold the span their parent implies. `ExceptionHandler` answers it 422 Unprocessable Entity carrying the SDK's message, which names the chunk and what is wrong, on every read alike: `GET /bytes/{ref}`, `GET /bzz/{ref}/`, `GET /soc/{owner}/{id}` (the four read routes declare the 422). Bee has no 4xx for it (a 404 `wrapped chunk cannot be retrieved`, or a 200 with an aborted body), and 400 stays for a malformed request: here the request is fine, the stored data is not.
- **A root chunk only read answers the wrapped chunk as it is, span and data.** `GET /feeds/{owner}/{topic}` and `GET /soc/{owner}/{id}` with `swarm-only-root-chunk: true` write the full payload of the wrapped chunk (`GetFullPayloadToByteArray`), as bee writes `wc.Data()`: a client asking for the root chunk gets the bytes that hash to its address, not the data alone.
- **Log events carrying a Mongo driver exception are filtered before Elasticsearch.** `Program.ConfigureLogging` enriches every event with its destructured exception through `Extensions/LoggerEnrichmentConfigurationExtensions.WithBeehiveExceptionDetails`, whose `Configs/Logging/MongoExceptionPropertyFilter` keeps only the scalar properties the driver declares on its exceptions (codes, names, messages, flags, error labels), outer or inner, from either copy of the driver the process loads (the Etherna fork Scrinium uses and the official `MongoDB.Driver` Hangfire.Mongo uses: the Hangfire storage failures are logged with the official driver's exceptions, which a filter knowing the fork's `MongoException` alone lets through whole), and drops its object graphs (`Command`, `Result`, `Query`, `WriteError`, `ConnectionId`, ...): destructured by reflection they expand into hundreds of nested fields that clash with the stream mapping, and Elasticsearch then answers 201 while redirecting the event to the failure store `logs-beehive-<env>::failures`, invisible in the main stream and to the sink. The sink's own failures (transport errors, hard rejections) reach Serilog's self log, enabled on the console.
- **Every relevant action logs through `Services/Extensions/LoggerExtensions`.** One `LoggerMessage.Define` delegate per event, grouped by level and alphabetical within the group, with an incremental event id (the header comment keeps the last one) and an extension method per event: never an inline `logger.LogInformation("...")` (CA1848). Levels: Information for a state change an operator follows (uploads, pins, postage batches, node registrations and alive transitions, the dev node toggling, task completions with their counters), Debug for high volume diagnostics (chunk pushes and chunk reads from the nodes, lock denials, the heartbeat skipped during a migration), Warning for a degraded condition the flow tolerated (a node failing a call, a swallowed read failure, a pin import whose job is gone), Error for work lost (a chunk the db refused, a failed push or funding). A failure caught and tolerated is always logged, never swallowed silently. `BeehiveChunkStore` takes the logger of its owner, so the log category names the flow (handler, service or task) that hit the store. `ExceptionHandler` logs every API exception by the status it answers: 500 at Error, 401, 409, 503 and 504 at Warning, the other client errors at Debug. `BeeNodeLiveInstance` logs the first heartbeat of a node and its alive transitions only, never every heartbeat.
- **`BeehiveChunkStore` asks one node per chunk, and saves what the nodes serve.** A chunk missing from `swarmChunks` and from the deprecated stores is read from the nodes: the store's `sourceNode` only, when given (the pins import reads the node's own local store); otherwise the nearest healthy node for a single hash, and for a batch of hashes the healthy nodes, ordered by overlay, each asked the partition of the hashes nearest to it. A node's not found is final, by decision (2026-11-16): bee's `GET /chunks/{hash}` looks in the node's local store and then retrieves the chunk from the network, up to 30 s per attempt, so its 404 means the network doesn't have the chunk either, and another node of ours would only repeat that retrieval, with its timeouts, on every missing hash. The one case a fallback on the other nodes would serve, a content pinned on a node and never pushed to the network, is an incident condition repaired by the re-import, not something every read should pay for (if it ever has to be covered, bee's `HEAD /chunks/{hash}` is a local-only probe, the sdk's `IsChunkExistingAsync`). A node not holding a chunk is logged at Debug with the hashes (`ChunksNotFoundOnNode`) and the chunk is left out of the answer; a node failing a read (an error status, a refused connection, a timeout) fails the fetch, and the failure propagates so `ExceptionHandler` answers the node's 503 or 504 instead of a misleading 404, and logs it there, once. What a node serves is saved in `swarmChunks` at once, `onSavingChunk` applied and the saving buffer flushed, by the single and the multi-hash fetch alike (`SaveFetchedChunksAsync`): a flow pinning through the store finds the documents on the db right after the read. A handler answering a stream over the store (`GET /bytes/{reference}`, `GET /bzz/{reference}/`, and `GET /soc/{owner}/{id}` and `GET /feeds/{owner}/{topic}` for a wrapped content) doesn't dispose the store when it returns, but registers it for disposal with the response (`Response.RegisterForDisposeAsync`): the stream reads the chunks through the store, and the store saves the ones read from the nodes, while Kestrel writes the body, after the handler returned; a store disposed by then fails the body with an `ObjectDisposedException` on its flush. The `IBeehiveDbContext.ChunksBucket` is typed as the driver's `IGridFSBucket`, so a store over a mocked db context can be tested (`InMemoryBeehiveDb` and `FakeBeeNode` in `Beehive.Services.Tests/Helpers`).
- **A failure while an api result executes is answered like one of its handler.** `ExceptionHandler.RunAsync` maps what a handler throws; `ApiExceptionMiddleware` (`Areas/Api`, registered after the routing, acting on the endpoints carrying an api group marker: `BeehiveApiMarker`, `SwarmApiMarker`, `SwarmV1ApiMarker`) maps through the same `ExceptionHandler.GetResult` what the result throws while it executes, after the handler returned: a `ChunkDataStream` is lazy, so a chunk missing from the tree surfaces at the first read of the body (`GET /bytes`, `/bzz`, `/soc`, `/feeds`). Until the first byte is written the response hasn't started, whatever `Range` was asked, since a file result reads before it writes: the middleware clears the response and answers the mapped status, a 404 whose message names the intermediate chunk and the children it couldn't fetch (`SwarmChunkChildrenNotFoundException`, a `KeyNotFoundException` of the sdk). After the first write the client already has a body cut short: the failure is logged at Warning at least, with the path, and the connection aborted. A request its client abandoned passes through, as outside the api. Don't probe a content in a handler to anticipate the failure, and don't wrap the stream.
- **Swarm types use the SwarmSdk libraries** (`Etherna.SwarmSdk` / `Etherna.SwarmSdk.Client`); the project migrated off bee.net. `IChunkService`/`IFeedService` from SwarmSdk are registered in DI. Persistence serializes Swarm value types via the custom serializers in `Persistence/Serializers/`; the API serializes them via the JSON converters wired in `CommonConsts`. Chunk payloads are stored in the documents of `swarmChunks` (next bullet).
- **A chunk is one document keyed by its hash.** `Chunk` lives in `swarmChunks` (repository `SwarmChunks`) with its `SwarmHash` as `_id` (`EntityModelBase<SwarmHash>`, the id serialized by `SwarmHashSerializer`), beside its payload, its single owner flag and the references of the pins holding it: no `Hash` member, no `Hash` index, every lookup is by `_id`. The repository is `ISwarmChunksRepository` (`Beehive.Persistence/Repositories`, implemented by `SwarmChunksRepository` beside it), and its creation carries the rule of the collection, so every writer follows it without knowing it: `CreateAsync` of a chunk held already doesn't fail, the held chunk takes the pins of the created one (`CreateOrAddPinsAsync` does the same and answers how many chunks were found held). A creation inserts a batch optimistically, without reading the db first: a batch of chunks beehive doesn't hold costs one insert. Scrinium creates a batch in a single ordered insert, inside a transaction on the replica set, so a hash held already, or created meanwhile by a concurrent writer, refuses the whole batch with a duplicate key (`MongoBulkWriteException` or `MongoWriteException`, E11000). Only then the repository reads which hashes of the batch are held, adds the pins of the created chunks to their documents (`$addToSet` by `_id`), and creates the others again in two halves, each inserted optimistically in turn; a single chunk refused is held, and takes the pins without a read. Every refusal leaves one more hash held and the halves shrink, so the save ends even when two uploads of the same content collide on every batch: an upload of a content beehive holds, with or without a pin, never inserts it twice and never loses its pin. Before 0.4.12 the chunks lived in two stores, now deprecated and only read, after `swarmChunks` and before the nodes: `Chunks` (`LegacyChunk`, the `chunks` collection of 0.4.0, object id and `Hash` member) and, before it, the GridFS bucket `chunks` (`ChunksBucket`, read with the secondary read preference, so a replica set without a secondary times out on it). A read never copies a deprecated chunk into `swarmChunks`, and nothing writes them but the pins: a pinning that meets a chunk held only in `Chunks` adds the pin to that document, and its migration moves it with its pins; a chunk held only in the GridFS bucket has no document to carry a pin, and the pinning counts it missing until it is migrated. The migration of both deprecated stores into `swarmChunks` is an operation the operator runs by hand, and their removal follows it in a later release: `MigrateChunksTask`, a Hangfire job on the `DB_MAINTENANCE` queue started by `POST /deprecated-chunks/migrations` or from the admin page `/admin/chunks-migration`, one at a time (`ChunksMigrationService` answers 423 while one runs, and every run leases `chunksMigrations/all`). It is not a Scrinium `DocumentMigration`: those run all together at every migration of the dashboard, one document at a time, and can't read GridFS. `ChunksMigration` (`chunksMigrations`) records a run with its counters per store (read, inserted, merged into a chunk held already, failed) against the totals the db estimated at its start (`GET /deprecated-chunks/migrations`; `GET /deprecated-chunks` estimates what is left). The job moves a page of `PageSize` documents at a time, first `chunks` then the GridFS files, through `IDeprecatedChunkStores`: it creates the page with `CreateOrAddPinsAsync` (counting the merged chunks; a chunk held already takes the pins of the moved one, two documents of the same hash end in one chunk with both pins), keeping the creation date of the moved chunk (the upload date of a file), and then deletes it from its store. A `chunks` document is deleted only while it carries the pins it was read with: one that took or lost a pin meanwhile stays, and is read and moved again, so a concurrent pinning never loses its pin. The documents read and the chunks saved leave the db context with their page (`StartTransientModelsScope`): a document read again deserializes its current content, not the instance loaded before, and a scan of the whole collection keeps no page in memory. Every chunk is verified before it is moved (`FindIntegrityFailure`), by the kind its document says: the payload of a content addressed chunk must hash to its hash (`SwarmCac.IsValid`), the one of a single owner chunk must carry the identifier and the signature of the owner that give it (`SwarmSoc.BuildFromBytes` with the hash, then `ValidateSoc`); a file of the bucket is a content addressed chunk. The documents of a page are verified in parallel, since hashing a 4 KB payload costs about 130 µs of cpu and a serial check made the move about a quarter slower; the files are verified as they are downloaded. A document that can't be read, a file whose name is not a hash, and a chunk that doesn't verify are logged with the reason, counted as failed and left in their store. A payload that is the chunk of its hash, but of the other kind than the stored one, is reported as such and left there too: the migration never corrects the kind by itself. The stores only shrink, so a new run goes on with what the previous ones left: a stop (`POST /deprecated-chunks/migrations/{id}/stop`, `StopRequestedDateTime`) ends the run at the end of its page as stopped, a cancelled job leaves the run running for the next performance of the job, and a run whose job is gone is failed when read, like the pins imports.
- **An old document shape stays readable through a secondary schema, and its rewrite is an operation, never code.** A renamed or reshaped element keeps the documents already stored readable through `AddSecondarySchema(<old schema id>, fix function)` on the model map (`ChunkPinMap` keeps the pre-0.4.1 pins, `Hash` + `EncKey`, readable this way); the fix function rebuilds the member in memory after the read, so a server side filter on the new element doesn't match those documents until they are rewritten on the active schema. That rewrite is run by the operator from the Scrinium dashboard (`/admin/db`, dry run first, then the real run, which takes the exclusive access of the instance running it): a `DocumentMigration` is never declared in `BeehiveDbContext.DocumentMigrationList` for it.

## Issue tracker

Bugs and features are tracked in Jira project **BHM** (https://etherna.atlassian.net/projects/BHM). Branch names follow `feature/BHM-<id>-<slug>` / `improve/BHM-<id>-<slug>` / `fix/BHM-<id>-<slug>` — match this when creating branches.

## Release process

Releases follow git flow: `dev` is merged into `main` with a merge commit, the merge commit is tagged `vX.Y.Z` and the tag push triggers the stable Docker Hub deploy (`.github/workflows/stable-release.yml`: the image `etherna/beehive` tagged `vX`, `vX.Y` and `vX.Y.Z`, built by the `Dockerfile` with its tests; GitVersion derives the assembly version from the tag, there is no manual version bump). The release is completed by a GitHub release on the tag, carrying the notes of the Jira fixVersion in the Scrinium style: a one paragraph summary of the release, one highlight per change with its issue key in parentheses, an "Upgrading from" section with the deployment steps (Hangfire storage, collections, configuration, api differences, dependency updates) and the full changelog of the fixVersion grouped by issue type in a collapsed `<details>` block. Every issue follows the same workflow: branch from `dev` (`feature/BHM-xxx-*`, `improve/BHM-xxx-*` or `fix/BHM-xxx-*`), tests and AGENTS aligned in the same change, commits only after human review, one PR per issue to `dev`. A hotfix line follows git flow too: `hotfix/X.Y.Z` (no `v`: the tag carries it) branches from `main`, its issues carry the hotfix fix version, branch from the hotfix branch and PR to it; the finished line merges into `dev` first and into `main` second, the `main` merge commit tagged `vX.Y.Z`; once both merges are pushed the line branch is deleted, locally and on origin, together with the issue branches it merged. Every push on `dev` deploys the unstable image (`unstable-release.yml`, tag `dev`); a hotfix branch deploys nothing until its tag.

**Which version is out and which line is open is read from git, never written here**: `git tag --sort=-v:refname | head -1` is the last release, `git log --oneline --decorate -1 <tag>` the commit it tagged, `git branch -r --list 'origin/hotfix/*' 'origin/release/*'` the open lines (none means the next release comes from `dev`), and `git log --oneline main..dev` what it will carry.

# Coding Style

## General Principles

- Keep commits clean: only include changes strictly necessary for the task at hand.
- A security fix keeps its commit message and PR title neutral: the Jira key and what changes, never the vulnerability. The write-up stays in the Jira work item, hidden until the fixed version is released; outside reporters are directed to [SECURITY.md](SECURITY.md).
- Keep the documentation wiki aligned: user-facing docs live in the sibling `beehive.wiki` repo (published at https://github.com/Etherna/beehive/wiki, checked out next to this one). Every change to the API, configuration, features, operations or architecture must be reported there in the same work line, on the wiki branch named like the code line (`dev`, `hotfix/X.Y.Z`); see its own `AGENTS.md` for its conventions.
- Never reference AI agents or assistants in commits or code — no agent names, no `Co-Authored-By` agent trailers, no "generated/assisted by" notes. Commit messages and code must read as the team's own work.
- Exceptions to these conventions are accepted when strictly necessary or when they significantly improve code quality. Justify with a comment where needed.
- All elements (usings, properties, methods, fields, enum members, etc.) are always alphabetically ordered within their respective sections.
- Primary constructors are preferred everywhere the constructor is a simple parameter assignment — not limited to DI services.
- Keep code clean: remove unused variables, dead code, and redundant imports.
- Don't extract a private helper method for logic used in a single place — inline it. Reserve helpers for code shared by two or more call sites (or when extraction materially clarifies an otherwise long, complex method).
- Every source file starts with the standard AGPL-3.0 copyright header (`// Copyright 2021-present Etherna SA` … see any existing file).

## Naming

- **Classes/Structs**: PascalCase (`BeeNodeService`, `ChunkPin`)
- **Interfaces**: `I` prefix (`IBeehiveDbContext`, `IPinService`)
- **Async methods**: always `Async` suffix (`CreateAsync`, `FindFeedUpdateAsync`)
- **Properties**: PascalCase (`ConnectionString`, `IsBatchCreationEnabled`)
- **Private fields**: `_camelCase` only when backing a same-named property (`_items` for `Items`); otherwise plain `camelCase`
- **Primary constructor parameters**: `camelCase` without underscore
- **Constants**: PascalCase, except the all-caps underscore style used for Hangfire queue names (`DB_MAINTENANCE`) — `CA1707` is disabled to allow these
- **Enums**: PascalCase type and members (`BeeNodeSelectionMode.RoundRobin`)
- **Namespaces**: `Etherna.Beehive.<Layer>.<Feature>` mirroring the folder under the root namespace (e.g. `Etherna.Beehive.Domain.Models`, `Etherna.Beehive.Services.Tasks.Cron`)
- **DTOs**: `Dto` suffix (`BeeNodeDto`); **API input models**: `Input` suffix (`BeeNodeInput`)
- **API handlers**: `<Feature>ApiHandler` implementing `I<Feature>ApiHandler`
- **Event handlers**: `On<Event>Then<Action>Handler` (e.g. `OnBeeNodeCreatedThenAddNodeStatusHandler`)
- **Hangfire tasks**: `<Name>Task` implementing `I<Name>Task`, with a `public const string TaskId`
- **Custom exceptions**: `Exception` suffix, always `sealed`

## Code Organization

- One class per file, filename matches class name
- Namespace mirrors folder structure exactly (under the `Etherna.Beehive` root namespace)
- Block-scoped namespaces: `namespace X { ... }` — NOT file-scoped
- Using directives inside the namespace block, always alphabetically ordered and kept to the minimum necessary
- No global usings — each file declares its own imports

## Comments

Principal comments (generally multiline, important):
```csharp
// Capital start, ending period.
// Continued on next line if needed.
```

Secondary/separator comments:
```csharp
//no space, no capital, no ending period
```

XML doc comments (`///`) document public API where they aid understanding (`CS1591` is disabled, so they are not mandatory on every public member).

## Member Ordering Within a Class

Use principal-style section comments to delimit groups, in this order:

```csharp
// Consts.
public const string TaskId = "myTask";

// Fields.
private List<Item> _items = [];

// Constructors.
public MyEntity(string name) { ... }
protected MyEntity() { }

// Properties.
public virtual string Name { get; set; }

// Methods.
public virtual void DoSomething() { ... }

// Helpers.
private void InternalHelper() { ... }
```

## Class Design

- `sealed` (often `internal sealed`) for service, handler, and event-handler implementations
- Primary constructors everywhere the constructor is a simple assignment
- Reflection-discovered types (event handlers, model-map collectors) are matched by namespace — keep them in the expected namespace

### Domain Entity Classes

- `public abstract` for base entity classes (`ModelBase`, `EntityModelBase`)
- `virtual` on all properties and mutating methods for Scrinium proxy support (lazy loading and change tracking), except members living in memory only (`EntityModelBase.Events`): those stay non-virtual, so reading them on a summary never triggers a load
- Use `public set` on properties only when external mutation is intended (e.g. `BeeNode.ConnectionString`); use `protected set` when the property requires validation or invariant enforcement, mutating it through a method
- Protected parameterless constructor for ORM deserialization:
  ```csharp
  #pragma warning disable CS8618 // Non-nullable field must contain a non-null value when exiting constructor.
  protected EntityName() { }
  #pragma warning restore CS8618
  ```
- Collection encapsulation with backing fields and collection-expression setters:
  ```csharp
  private HashSet<SwarmHash> missingChunks = [];
  public virtual IEnumerable<SwarmHash> MissingChunks
  {
      get => missingChunks;
      protected set => missingChunks = new HashSet<SwarmHash>(value ?? []);
  }
  ```
- Equality is by ID for entities (implemented in `EntityModelBase<TKey>`); value objects compare by value

## Async Patterns

- Always suffix with `Async`
- `CancellationToken cancellationToken = default` as the optional last parameter (non-nullable, `default` — not `CancellationToken? = null`)
- Return `Task` or `Task<T>`, never `async void`
- **No `ConfigureAwait(false)`** — this is an ASP.NET Core application, and `CA2007` is disabled in `.editorconfig`. (This is the opposite of the SwarmSdk *library* rule.)

## Null Handling

- Nullable reference types enabled (`<Nullable>enable</Nullable>`)
- `ArgumentNullException.ThrowIfNull(param)` for parameter validation — no explicit `nameof`, the parameter name is captured automatically
- `is null` / `is not null` (not `== null`)
- Prefer `null` over `default` as default value for optional reference parameters
- `??` and `??=` operators

## Formatting

- Allman braces (opening brace on new line)
- 4-space indentation (2 spaces in `.csproj` files, per `.editorconfig`)
- Expression-bodied members for single expressions:
  ```csharp
  public virtual bool IsSucceeded => IsProcessed && missingChunks.Count == 0;
  ```
- LINQ method chains: one operation per line, aligned
- Blank line between member sections

## C# Language Features

- Pattern matching: `is`, `is not`, type patterns, property patterns
- Switch expressions for multi-branch returns
- Primary constructors everywhere applicable
- Collection expressions: `[]`, `[..spread]`
- Prefer collection expressions over constructors to initialize any collection: `[]` not `new()`, `["a", "b"]` not `new List<string> { "a", "b" }`. Use a constructor only when a collection expression can't express the intent (e.g. presizing capacity, or building a specific set type like `new HashSet<T>(value ?? [])`).
- Target-typed `new()` when type is clear from context (for non-collection types)
- Tuple deconstruction for multiple return values
- Span/`Memory<byte>` and ranges (`data[..32]`, `data[cursor..]`) for byte-level slicing of chunk data — avoid unnecessary copies

## LINQ

- Method syntax preferred over query syntax
- Query syntax only for complex join/groupby with multiple `from` clauses (e.g. the reflection queries in `BeehiveDbContext`/`ServiceCollectionExtensions`)
- Fluent chaining, one operation per line for readability

## Dependency Injection

- Constructor injection exclusively
- Reflection-based event-handler discovery (by namespace) in `AddDomainServices`
- `AddScoped` for domain services, the DbContext, and API handlers
- `AddTransient` for Hangfire tasks
- `AddSingleton` for `BeeNodeLiveManager` and options/configuration objects
- `AddHostedService` for background workers

## Testing (xUnit + Moq)

- `[Fact]` for basic tests, `[Theory]` with `[MemberData]` for parameterized cases (e.g. the per-schema-version deserialization tables)
- AAA pattern with section comments: `// Setup.`, `// Action.`, `// Assert.`
- xUnit assertions: `Assert.Equal()`, `Assert.NotNull()`, `Assert.Throws<T>()` / `Assert.ThrowsAsync<T>()`
- Moq for mocking: `new Mock<IBeehiveDbContext>()`; entities under test are often built as `Mock<TEntity>` with `Setup(...)` on virtual members
- The test project mirrors the project under test (`Beehive.Persistence.Tests` mirrors `Beehive.Persistence`); add a new mirror test project only when a layer grows logic that needs covering
- When adding or changing a `ModelMap`, add a deserialization test that pins the new map GUID against a representative stored document (see `BeehiveDbContextDeserializationTest`)
